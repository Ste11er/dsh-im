# QQ 收不到消息：重连超时修复验证

日期：2026-10-30（北京时间）。用户补充：故障发生时 DSH 网页仍可打开，但无法收到 QQ 消息。因此按 QQ 连接/入站事件链路修复已复现的问题，未归因为 DSH Web 服务退出。

## 变更

- 仅适配固定版本 QQ SDK 1.0.4 的认证请求和网关地址读取。原计时器收到响应头后即撤销，正文卡住会阻塞 token singleflight 或网关恢复；新计时器覆盖 fetch 和完整正文读取，超时直接 AbortController 取消实际请求。
- 沿用 SDK 认证 10,000ms、网关 HTTP 30,000ms 默认值。SDK 的 token 缓存、singleflight、后台刷新、session resume、重连退避不变，HTTP 429 仍进入 SDK 60 秒退避。
- 连接取消等待提前注册，避免停机发生在 token/网关读取期间时错过 abort 事件。
- 服务端 RECONNECT 也计入实际调度的重连次数，修复“重连了却仍计为 0”。
- `gatewayTransport` 新增连接阶段、最近断开原因/关闭码/时间、最近 32 次状态变化、原始 DISPATCH 和消息事件计数。连接恢复会清除当前故障状态，保留最近故障证据；不记录消息内容或凭据。
- 诊断状态保留于当前 runtime，runtime 被重建后重置；断开元数据同时写入 DSH 本地日志。没有因群内安静或单纯缺少聊天消息强制重连。

## 修复前失败证据

- `request-tests-red.log`：真实 SDK 认证/网关正文挂起不能按测试期限结束，停机取消也会卡住。
- `recovery-tests-red.log`：启动取消等待未结束；服务端 RECONNECT 后计数仍为 0；恢复后没有关闭原因。
- 诊断探针原始模式（`gateway-body-probe.mjs --legacy`）保留旧 SDK 读取行为，250ms 后依然 isConnecting、无 WebSocket、无重连计时器。

## 修复后验证

1. 14 项目标回归通过，包含真实 SDK / 本机 HTTP / WebSocket 的网络故障注入。
2. 恢复场景：连接先成功 → WebSocket 断开 → 第二次网关查询响应正文挂起 → 请求超时且实际 socket 关闭 → 按 SDK 退避第三次查询 → session resume → 连续收到模拟群聊和私聊事件。
3. 认证正文超时后，SDK pending singleflight 被释放，可重新获取 token，成功 token 继续命中同一缓存。token TTL 数字字符串也覆盖在真实 facade 集成中。
4. 原诊断探针默认路径通过：250ms 时 isConnecting=false，已经调度重连，保留 qq-gateway-timeout。
5. 完整回归：4254/4254 通过，无失败、取消或跳过。
6. 构建、包内容验证、Node 语法检查、git diff --check 均通过。

既有心跳测试原本在第四次心跳发送后就可能断言第四次 ACK 已返回，本次让等待条件明确等待该 ACK，保留原有断言；未调整生产心跳周期或放宽协议超时。

## 部署与保留

修复已构建并重新启动 DSH，真实 QQ 已完成 READY。部署约 132 秒后仍为 connected，心跳回执比发送晚 66ms，无重连/错误；尚无新的用户测试消息。管理 API 验证配置、群会话绑定、工作区、owner 权限、长期记忆开关均不变，原有 3 个游戏数据文件已备份且内容不变。备份和部署结果位于 `outputs/runtime/qq-recovery-timeout-fix/`；启动日志含认证 URL，不能直接对外分享。
