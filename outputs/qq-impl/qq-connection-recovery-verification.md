# QQ 群聊和私聊同时停止接收（2026-10-29）

用户反馈原活跃群普通消息、@、私聊同时消失。手动重连后仅第一条私聊成功，随后再次停止接收。

## 证据与边界

故障时只有一个 DSH web 进程，面板仍称 connected。手动重连后的私聊会话确实完成了一个回复回合，后续群消息未进入 SDK 首个消息中间件。检查同一进程的网关 TCP：仍为 ESTAB、持续发送数据，但最后接收距检查约150秒。说明本次不是群级接话判断、冷却或前一回合未完成。

SDK 1.0.4 的 `GatewayConnection` 只定时发送心跳，`HEARTBEAT_ACK` 分支为空，没有缺失应答后的断线检测；`QQBot` 也没有把关闭/重连状态传给 Runtime。Runtime 仅凭历史READY保持ready，Controller据此跳过重建。

本机真实WebSocket模拟网关持续不回ACK，旧SDK结果：ready=1、发出8次心跳、ACK=0、连接仍OPEN；断线检测断言失败。该实验确认缺陷能复现“假在线”，但原故障前没有记录每个ACK，不能把所有历史断收都追认为这一个网络触发原因。原始TCP/会话只读核验也不能确认上游未回包发生在QQ还是网络中间层。

## 修复

固定SDK 1.0.4协议适配 `src/channels/qq/gateway-connection.mjs`：

- 心跳发送后等待一个QQ HELLO给出的完整间隔；下次心跳时仍无ACK则终止失效socket，沿用SDK的重连、认证和退避。没有群消息不构成断线依据。
- HELLO及READY/RESUMED握手以现有20秒连接预算限时，卡住则断开重连。
- 每代socket的open/message/close/error回调绑定该socket身份，旧连接迟到事件不能清理新连接。
- SDK连接中、等待重连或失败立即同步Runtime。只有READY/RESUMED恢复就绪，面板不再只看上次成功。
- Controller监督器保留SDK正在执行的重连退避，不每15秒重建客户端并重置限流预算。SDK结束/耗尽后仍由既有监督器处理。
- 状态接口补充不含消息正文、token、完整群标识的gatewayTransport：心跳发送/ACK/收帧时间、间隔、重连次数和原因。

已有token刷新、群消息/私聊解析、中间件、消息权限、会话和游戏进度沿用原实现。
