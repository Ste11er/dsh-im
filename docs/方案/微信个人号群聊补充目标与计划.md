## 1. 背景与范围

### 1.1 动机

仓库外存在一份调研（`/home/stella/Project/wechatbot/md/`，整理于 2026-10-03），目标形态是**个人微信号作为机器人加入普通微信群**：白名单私聊、群内 @问答、连续追问，并偶尔参与群聊闲聊，模型用 DeepSeek。

本文把该调研的目标能力与本仓库（dsh-im）的实际能力逐条对照，给出**补充目标与落地计划**。

### 1.2 现状一句话

dsh-im 的「微信」渠道是**腾讯 iLink 官方单聊机器人**：扫码绑定、长轮询收发、只支持点对点私聊，群能力为零，且不是"开关未打开"而是"协议层没有"（见第 3 节）。因此调查文档的核心诉求——个人微信号进普通微信群、群内 @问答、未 @ 接话——当前**完全未覆盖**；而它要求的控制类能力（发送预算、安静时段、dry-run、持久暂停、原文不落盘）本仓库也**一项都没有**。

## 5. P0 控制规范要点

完整规范（字段、状态机、判定顺序、交互细节）见 `controls-spec.md`（本 run 工作产物 `outputs/wechatbot-supplement/`），本文只保留决策要点。

### 5.1 拦截分层与判定顺序

| 层 | 含义 | 是否受控 |
| --- | --- | --- |
| L1 | 入站（授权） | 否，由访问策略负责 |
| L2 | 被动回复（含 `/stop`、审批提示等控制反馈） | **仅 dry-run 可观测**；暂停、预算、安静时段均不拦 |
| L3 | 主动投递（`sendProactiveText`） | 是 |
| L4 | 后台结果补发（延迟投递） | 是 |

判定顺序：**账号级持久暂停 → dry-run → 发送预算/限频 → 安静时段 → 真实发送**。

### 5.2 五项控制

| 控制 | 触发点 | 作用域 | 默认值 | 重启行为 | 可观测信号（设计） |
| --- | --- | --- | --- | --- | --- |
| 发送预算/限频 | L3、L4 前的出站闸门；**不拦 L2** | 账号级为主，可选会话级子预算 | **关闭**（不限额） | 开关与阈值持久化；窗口内已用计数建议一并持久化 | `budget: { enabled, window, limit, used, resetsAt }` + 诊断（不含正文） |
| 安静时段 | L3、L4 出口；**不拦 L2** | 账号级默认，可会话级覆盖 | **关闭** | 窗口配置与待投递队列持久化（队列持久化可行性 `未核验`） | `quietHours: { enabled, window, timezone, active, nextResumeAt, queued }` |
| dry-run | 出站闸门最外层之一，拦 L3/L4 与连接测试；默认不拦 L2 | 账号级，可会话级覆盖 | **关闭**（真发） | 开关持久化；预览记录内存态，重启清空 | `dryRun: { enabled, suppressedCount, lastPreviewAt }` |
| 账号级持久暂停 | 出站闸门最外层，优先级最高；不拦 L1/L2 | 账号级 | **未暂停** | **必须持久化**，恢复需显式操作 | `paused: { active, reason, since, by }` + 面板横幅 |
| 渠道侧不新增持久化 | 渠道 `state-store` 写入点与渠道级正文日志 | 渠道 × 账号 | **不改变现状**（提供 `full`/`minimal`/`off` 三档，默认 `full`） | 模式持久化；切换后历史数据清理策略 `未核验` | `rawRetention: { mode, since }` |

### 5.3 两条已确认的改写（必须遵守）

1. **安静时段默认关闭，且只约束主动投递与后台补发，不约束被动回复。**
   理由：被动回复被静默会破坏 `/stop` 反馈、延迟补发和审批闭环——用户看不到控制命令反馈，审批提示也会消失。
2. **原「原文不落盘」改写为「渠道侧不新增持久化」。**
   准确含义是渠道适配器不再额外写一份原文/日志；**不是**「聊天记录不留存」。DSH 会话本身仍必须保存上下文才能多轮对话，这不在本控制作用域内。

### 5.4 与既有语义的交互（要点）

- **与 `/stop`**：五项控制都不得阻止 `/stop` 的入站解析与反馈回复；`/stop` 也不改变任何控制的配置。
- **与延迟投递**：静默等待与预算拒绝**不得消耗** `attempts`（`src/channels/shared/deferred-delivery.mjs:157`：`attempts >= 3` 即置 `failed`），状态保持 `pending`、退避重排。否则三次静默/预算拒绝就会永久丢掉一条结果。
- **与 `deliveryOutcome: 'unknown'` 的区别**：本地控制造成的「尚未尝试」可安全重试；平台结果未知按既有规则**不自动重试**（`deferred-delivery-coordinator.mjs:172`）。两者不得混为一谈。
- **与审批闭环**：暂停/预算/安静时段均不得取消待审批项、不得触发自动拒绝或缩短超时（默认 60 分钟，`src/channels/shared/harness-approval.mjs:24`）；被出站控制拦下时，必须保证 Web 端仍可看到并处理。
- **与主动投递**：被控制拦下时不消耗 `context_token`；平台侧额度/上下文错误与本地预算/暂停来源不同，诊断需可区分（`PROACTIVE_DELIVERY.md:325`）。
